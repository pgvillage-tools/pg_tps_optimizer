    The password is never printed.

    Columns¶

    Column Meaning
    Date time When the step finished
    Clients The number of clients (connections) running the workload in this step
    Performance: TPS Transactions per second, as measured by the clients
    Performance: Latency (usec) The average time a transaction took, in microseconds
    Performance: TPS/Latency TPS divided by latency: a measure for how efficiently the clients are served
    Postgres: TPS Transactions per second according to PostgreSQL (pg_stat_database), over the whole step (also while waiting for it to become stable): committed and rolled back transactions in all databases, so including other activity on the server. PostgreSQL updates these statistics about once per second, so short steps can differ more from the clients' TPS
    Postgres: wal kB/s The amount of WAL (write-ahead log) PostgreSQL wrote per second during the step, in kB, for the whole server

    A * before the TPS means the step didn't become stable within --max-wait: the numbers are the mean of the last samples, but they varied more than --spread. More clients, or a busy server, usually need more time; try a larger --max-wait.

    JSON output¶

    With --output json (or PGTPSOUTPUT=json), pg_tps_optimizer prints one JSON document at the end of the run, instead of the table. The progress messages (Initializing, the settings, Finished) go to stderr, so stdout only has the JSON:

    pg_tps_optimizer --output json > results.json

    {
  "version": "0.3.0",
  "settings": {
    "min_clients": 1,
    "max_clients": 200,
    "max_wait_seconds": 10,
    "min_samples": 10,
    "spread": 10.0,
    "transactional": false,
    "prepared": false
  },
  "steps": [
    {
      "timestamp": "2026-10-24T07:49:41.123456+02:00",
      "clients": 1,
      "stable": true,
      "tps": 4013.761,
      "latency_us": 498.0,
      "tps_per_latency": 8.06,
      "postgres_tps": 3655.436,
      "wal_kb_per_sec": 263.2
    }
  ]
}
    Field Meaning
    version The version of pg_tps_optimizer
    settings The settings of the run: the range of clients, --max-wait (in seconds), --min-samples, --spread, --transactional and --prepared
    steps One entry per step, in the order they ran
    timestamp When the step finished (RFC 3339, local time)
    clients, tps, latency_us, tps_per_latency, postgres_tps, wal_kb_per_sec The columns of the table (see Columns)
    stable false for a step that didn't become stable within --max-wait (the * in the table)

    When a step got no samples at all (shown as ? in the table), its measurements are null. No transaction finished in that step, so the run stops after it, with exit code 1 (see Exit codes); the JSON document is still printed.

    Graph¶

    With --graph <file> (or PGTPSGRAPH), pg_tps_optimizer also draws a graph of the TPS per number of clients, with the numbers of clients evenly spaced on the x axis (1, 2, 3, 5, 8, ...):

    pg_tps_optimizer --graph tps.png
pg_tps_optimizer --graph tps.svg

    The graph is a PNG, or an SVG when the file name ends with .svg; --graph-format png|svg sets the format explicitly. An SVG scales without getting blurry, and is easy to put on a web page.

    Comparing runs¶

    To compare runs, save each run with --output json, and draw them together with --graph-input. pg_tps_optimizer then doesn't run (or connect), but draws one line per JSON report, named after the file:

    pg_tps_optimizer --output json > 4cpu.json    # on one setup
pg_tps_optimizer --output json > 8cpu.json    # on another one
pg_tps_optimizer --graph compare.svg --graph-input 4cpu.json --graph-input 8cpu.json

    Steps without measurements (? in the table) are left out of the lines.

    Interpreting the results¶

    In the example above (PostgreSQL 18 in a small virtual machine):

    • TPS grows quickly up to 21 to 34 clients (about 21,500 TPS), and hardly grows after that: the server is saturated.
    • Latency keeps growing with every step: from 0.5 ms with one client to almost 12 ms with 144 clients. More clients means more waiting.
    • TPS/Latency is highest at 2 to 3 clients: transactions are fast, but the server isn't used fully yet.
    • Postgres TPS follows the TPS of the clients, so there was no other noticeable load on the server. wal grows with the TPS: about 60 to 70 bytes of WAL per transaction.

    So, depending on what you need:

    • for (nearly) the most TPS, use around 34 clients;
    • for the lowest latency with reasonable TPS, use 3 to 8 clients;
    • more than 55 clients mostly adds latency. That's a good upper limit for a connection pool in front of this server.

    The numbers depend on the hardware, the PostgreSQL configuration and the workload. By default, pg_tps_optimizer runs a very small update (see the workload), so it shows the limits of the server and the connection handling, not of your own queries. To see those, run your own query with --query.
